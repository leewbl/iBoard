模型适配器从本目录 `glm.ini` 读取用户提供的密钥，以环境变量交给 Claude Code；密钥不放入参数、任务记录或测试容器。`glm.ini` 已加入忽略列表，文件权限为当前用户可读写。

模型调用超时或 Python 收到键盘中断时会清理 Claude 的进程组；系统强制结束工作台进程时无法保证执行清理，恢复前应先检查残留进程和容器。

### 工作台插件原型

从终端加载本地插件（插件加载不代表任务已执行）：

```bash
claude --plugin-dir "$WORKBENCH_DIR"
```

在 Claude Code 中运行 `/agent-workbench:optimize`，并提供明确的任务、目标仓库及个人 fork。具体输入应包括截图和日志（如有）。若运行环境缺少真实隔离环境或其他强制条件，工作流会报告阻断，不在宿主机替代执行。

也可以从插件目录用单条命令创建并运行一个明确指定的非界面任务，例如：

```bash
python3 -m workbench.start --id my-task --repo /path/to/repo \
  --issue-file /path/to/request.txt --source '用户提供的问题描述' \
  --kind bug --surface non-ui --iterations 3 --seconds 3600 \
  --image local-test-image --pr-repo owner/personal-fork \
  --required-ci-workflow CI
```

将 `--issue-file ... --source ...` 换成 `--issue-url https://github.com/owner/repo/issues/123` 可读取指定的 GitHub Issue；不会自动领取其他 Issue。镜像须已存在本地，仓库须干净；创建后会保存任务路径和原始问题副本，后续失败时保留工作区和记录。该入口不会自动下载 Issue 附件。

指定 `--pr-repo` 时必须同时通过 `--required-ci-workflow` 指定至少一个必需的 GitHub Actions 工作流名称；该参数可重复，例如再加 `--required-ci-workflow 'Security Review'`。名称须与仓库 Actions 中的工作流名称完全一致，且工作流必须由对应 PR 触发。工作台会将名称保存到任务记录，等待对应 PR、基线及候选提交上的工作流成功；缺失、失败或身份不匹配时不交付。未指定 PR 的本地验证可以省略该参数。原有交付门禁仍会检查全部状态，因此条件跳过或中立状态可能导致交付停止，需要查明原因。

交付门禁目前只接受工作流的首次运行。GitHub 对失败作业的局部重跑只返回该次重跑的作业，不能据此证明所有原始作业均已通过；若运行已被重跑，须创建新的完整工作流运行，等待其首次运行完成并重新验证。

可重复指定 `--log-file /path/to/log.txt`，最多提供八个 UTF-8 文本日志；总问题材料不得超过 100000 个字符。工作台保存日志原文、文件哈希和合并后的问题材料供模型使用，并将日志视为不可信数据。恢复时会检查问题材料、日志快照和清单是否与原任务一致；这些本地哈希不是防篡改安全边界。旧版未绑定问题内容、且已经开始执行的任务不能自动恢复，需要先保留证据并人工处理。

可重复指定 `--screenshot /path/to/image.png`，最多四张 PNG、JPEG 或 WebP 图片，每张不超过 5 MB。工作台保存原图，并用编程套餐中的 `glm-5.3-flash` 生成供任务规划参考的文字描述；描述可能出错，不是修复证据。当前已测试三张纯色图片及一张合成的 503 错误截图，不代表复杂截图识别已充分验证。

新启动的文本、日志和截图任务会保存运行设置。在时间预算仍有效、任务处于暂停状态时，可运行 `python3 -m workbench.resume --task <任务记录>` 按原设置继续，并检查已保存的输入哈希。截图描述已成功的部分不会重复调用。旧任务或中断发生在恢复状态建立之前的任务可能缺少所需记录；中断在代码实现或修复阶段时，流程会停止并保留现场供检查，不会自动重做。启动、恢复、检查、发布、交付和任务记录命令通过任务目录中的文件锁拒绝同时操作同一任务；任务运行时记录命令包括 `pause` 也会被拒绝。直接修改文件不会受锁约束，锁文件不能在运行中删除。

界面任务的实验流程要求计划提供已跟踪的浏览器截图脚本，并将 PNG 写入 `WORKBENCH_SCREENSHOT_PATH`。独立验证者运行截图脚本后，工作台保存图片、容器报告和哈希，并调用视觉模型提供审查描述；最终审查必须引用截图哈希。也可直接通过 `workbench.workflow check --kind screenshot` 调用底层收集能力。文件和哈希无法单独证明图片反映目标界面，审查仍须核实截图脚本及可见结果。已验证独立浏览器截图与视觉描述，完整界面任务流程仍在试验中。

本地界面练习中曾发现截图证据被后续记录覆盖；修正后，另一个按钮状态练习使用真实 GLM、浏览器、视觉模型完成复现、修改和独立审查，并按每项验收条件记录证据引用。任务未指定 PR，停在交付阶段；记录位于 `.sandbox-check/ui-button-e1fc4a3c/tasks/ui-button-live/`。这是隔离练习，尚未验证真实 GitHub 交付或所有界面类型。

最终独立审查必须逐条说明验收条件，并引用经哈希绑定的运行报告；源码静态条件可以引用与提交绑定的代码差异。整个审查仍须引用运行报告，界面任务还须引用独立截图报告。旧版仅包含 PASS 的审查不能通过新的交付门禁；在预算有效、候选提交未变的情况下，可先恢复任务，再运行 `python3 -m workbench.autopilot --task <任务记录> --issue-file <问题材料> --image <镜像> --reverify` 重跑验证，原有审查记录会保留。

问题描述、日志正文及提供的图片会发送给配置的 GLM 模型服务；提交材料前请自行移除不希望发送的凭证和其他内容。

对于缺少 `input-stage.json` 和 `autopilot.json` 的暂停旧任务，可用独立接纳入口创建新任务并重新验证：

```bash
python3 -m workbench.adopt --legacy-task /path/to/old/task.json --id new-task \
  --tasks-root /path/to/tasks --workspaces-root /path/to/workspaces \
  --image local-baseline-image --pr-repo owner/personal-fork
```

该入口当前只支持非界面问题，且旧任务不能有未迁移的附件。它保留旧任务，将现存问题文本标记为接纳时重新绑定的输入，并保存旧任务快照；由于历史摘要缺失，无法证明现存文本与原始输入完全相同。新任务以旧基线重新规划和复现，复现经独立确认后才接纳旧工作区当前的干净候选提交，并重新执行完整独立验证及现有 CI 和交付门禁。旧任务与原 PR 不被直接修改；新任务使用新分支和新 PR。提交进入 main 后，GitHub可能将原 PR 标记为间接合并。镜像必须与旧基线的全部受版本控制源码一致，候选镜像通过重建源码层得到；这不保证已有构建产物适用于候选代码。旧任务明确取消的时间和迭代上限会被保留；单次操作仍有超时。创建新任务时中断，可能留下部分任务和工作树；部分情形可用下述命令恢复，其余情形应保留现场，检查后可使用新的任务 ID 重新开始。该接纳入口已用于本次真实试点，完成从新基线复现到自动合并；准备中断的完整事务恢复仍不支持。

如果接纳创建已写入完整任务记录，但写入 `input-stage.json` 前中断，可在可信本地环境中显式运行：

```bash
python3 -m workbench.adoption_stage_repair --task /path/to/tasks/new-task/task.json \
  --tasks-root /path/to/tasks
python3 -m workbench.resume --task /path/to/tasks/new-task/task.json
```

修复命令要求暂停状态的完整接纳记录、原始输入及旧任务快照可核对，且新工作区干净地停留在记录的基线；它检查候选提交、验收条件、隔离设置和 CI 策略依据，不替代后续基线复现和独立验证。可信任务根目录可包含系统提供的路径别名，根目录以下不得使用符号链接。此命令使用工作台锁协调协作进程，不防御其他本机进程在检查期间恶意替换路径。如果 Git 工作树创建中断且缺少完整任务记录，命令会拒绝修复；保留现场检查，不会自动接管或删除工作树。

任务记录工具：

```bash
python3 workbench/cli.py --help
python3 workbench/cli.py init --help
python3 workbench/cli.py gate --help
```

本地测试与插件格式检查：

```bash
python3 -m unittest discover -s tests -v
claude plugin validate .
```

自动流程的 `--source-mode image` 支持将 `--image` 作为基线镜像、`--candidate-image` 作为候选提交的镜像，并可用 `--memory-mb` 调整容器内存限制。每次检查前都会核对镜像内的受版本控制文件与当前提交是否一致。

指定的 CI 工作流失败时，工作台仅在运行、提交、PR 和基线可核对，且每个失败作业都有完整、大小受限的失败注释时，使用这些不可信数据尝试修复。修复占用一次迭代，并重新执行原有验证和独立审查；通过后才以旧提交为条件更新同一个 PR。失败信息不足、作业被取消、预算耗尽或远程状态变化时会暂停。镜像模式需要 `--build-source-image` 才能自动验证修复后的新提交。此 CI 修复路径目前仅经模拟测试，尚未完成真实端到端验证。

也可用 `--build-source-image` 自动将每次候选提交的源码叠加到已核对的本地基线镜像；它不安装依赖，也不编译程序。项目需要重新安装依赖或重新编译时，应提供按该提交构建的候选镜像，不能认为源码文件一致就代表构建产物正确。新镜像会占用磁盘空间；自动生成的镜像暂不自动删除。真实 Docker 集成检查可通过 `WORKBENCH_DOCKER_TEST=1 python3 -m unittest discover -s tests -p test_source_image_integration.py -v` 运行，需要本地已有 `node:24-slim`。

## 交付规则

问题必须先在基线提交复现，再在最终提交独立重跑并提供解决证据；无法复现则保留调查记录。需求须有功能说明、测试结果及界面截图；无界面时可用实际日志或请求响应。任何验收条件变更必须记录原因和依据，不能因通过困难而降低条件。真实 PR 合并前，还必须验证远程 PR 头、基础分支和所需检查；仅凭本地 `gate` 通过不能自动合并。

PR 正文使用绑定提交和哈希的独立沙箱报告，列出复现、修复和测试的退出状态及有限的真实日志摘录；摘录会移除常见凭证、URL、邮箱、路径和控制字符，但不能保证识别所有敏感内容，也不能代表完整日志。功能任务的文档链接指向候选提交中的已验证文件。界面任务将独立审查引用的截图和绑定清单放在个人 fork 的孤立证据分支，以认证 GitHub API 核对远端内容后，在 PR 中链接到固定证据提交；截图不会进入 main。发布图会删除 PNG 的文本、EXIF 和时间块，保留图像、动画、透明度及色彩配置，清单记录原图与发布图的哈希；如果 EXIF 方向无法安全移除则拒绝发布。ICC 和其他保留的视觉/扩展块仍可能包含元信息；截图发布路径目前只经过模拟测试，隐私也取决于截图本身的内容。

问题来源如果是目标个人 fork 中明确指定的 GitHub Issue，新任务会保存原始地址；确认对应的验证提交已合并后，工作台可关闭该 Issue。关闭失败时保留交付阶段，恢复后不重复合并。上游仓库 Issue 不会由个人 fork 工作台关闭；旧任务未保存原始地址时也不会自动关闭。该行为目前只有模拟测试，尚未对 GitHub 真实执行。

未受保护分支的快速前进推送会使候选提交直接进入 `main`，GitHub 随后可能将对应 PR 标记为间接合并。推送前检查分支保护和 PR，但 GitHub 不提供把这些检查与推送合为一个操作的方法；如果检查后保护规则或 PR 头发生变化，可能已推送经验证的旧提交，却无法确认 PR 合并。间接合并也可能绕过 PR 保护；有保护或无法确认分支状态时不会主动采用此路径。本次个人 fork 已通过该路径完成真实写入和合并。受保护分支的真实合并仍未实测。
